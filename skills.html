Methods

Turn solved problems into reusable skills

Every assistant owner has had this experience: you explain a task, the assistant works through it, makes a few mistakes, and eventually gets it right. You ask for the same thing next week — and it starts from scratch. The clever workaround it found on Tuesday is gone, because nothing kept it.

That is the difference between a one-off solution and a skill. A one-off solution evaporates the moment the conversation ends. A skill is the same solution written down as a recipe: inputs, steps, tools, failure modes, and a way to check the result. Written once, it compounds — every future run is faster, cheaper, and more reliable than the first.

A skill is not a prompt pack. A prompt pack is a clever sentence you copy and hope still works. A skill is a problem you have already beaten, distilled. Here is the recipe I use.

The recipe

  1. Work a real problem to a verified result. Do not write a skill for a hypothetical task. Run the actual job end to end, and confirm the output is genuinely right — not plausible, right. If you have not seen the finished result work, you have nothing to distill yet.
  2. Write down what actually worked. Note the inputs the task needed, the steps in order, the tools used, and the failure modes you hit along the way. Pay special attention to the mistakes: the ways the task went wrong are the most valuable lines in the document.
  3. Make it reproducible. Turn your notes into a standing document: clear instructions, a short prompt guide with example inputs, any helper scripts the task relies on, and a verification step at the end. Someone reading it cold — including your assistant next month — should be able to run it without improvising.
  4. Encode the hard-won rules as rules, not hopes. Every workaround you discovered the expensive way becomes an explicit instruction: "always do X," "never do Y," "if Z happens, stop and skip." Vague intentions drift; written rules hold.
  5. Run it again to prove the recipe. Execute the task once more using only the written skill. If the result holds, the skill is real. If it wobbles, the recipe was incomplete — fix the document, not just the run.

What makes a skill good, and what makes it brittle

Good skills share a few habits:

  • A description that says when to use it. The skill should name the situation it covers, so it gets picked up at the right moment and ignored the rest of the time.
  • Explicit failure handling. Things will be refused, time out, or come back broken. A good skill says what to do in each case — usually: skip it, move on, retry at most once. Without this, the assistant improvises under pressure, which is when the expensive mistakes happen.
  • A verification step before anything is announced. Check the output against reality — duration, format, content, whatever applies — before calling the job done. Success is a checked fact, not a feeling.
  • Rules learned from scars, written down. Each rule should trace back to something that actually went wrong.

Brittle skills do the opposite: they assume the happy path, encode no limits, and leave the assistant to guess when reality deviates. They work in the demo and fail in production.

A worked example

I generate and stitch short AI video clips into finished pieces. The first few projects were hand-run, and the same friction kept appearing: cuts for very short videos were allocated badly, spoken lines landed in the middle of clips so trimming chopped them in half, and clips the model refused would get retried until the run stalled.

After the third project, I stopped hand-running and wrote the skill. It now contains the full method: a short description of when to use it, step-by-step instructions, a prompt guide, an ffmpeg build script, and verification steps — probe the final file's duration and streams, and spot-check frames before declaring it done. The scars became standing rules, including:

At most one quoted dialogue line per clip prompt. Music-driven pieces get no dialogue or on-screen text. If a clip is refused, skip it — one retry maximum, never more.

Every video since has been produced by running that skill rather than re-deriving the method. The open-source agent community arrived at the same place independently: OpenClaw standardized the SKILL.md format, and its ClawHub marketplace treats skills as durable, shareable artifacts — complete with security scanning before installation.

Start with whatever you solved most recently. Write down what worked, what failed, and how you knew you were done. Your second solved problem will be cheaper than your first — and by the fifth, you will wonder how you ever worked without the file.
